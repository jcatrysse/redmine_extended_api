Major, app/controllers/extended_api_issue_histories_controller.rb:173
Problem: Unvalidated content_type can exceed the DB column limit and cause a 500. The controller assigns cols[:content_type] = given[:content_type].to_s and then performs update_all, bypassing validations. In Redmine, attachments.content_type is a varchar with a length limit (typically 255). On PostgreSQL, an overlong value raises PG::StringDataRightTruncation, yielding a 500 instead of the documented 422 “invalid” error.
Concrete failure: An admin calls POST /extended_api/issues/1/history.json with attachments: [{token: “…”, author_id: 1, created_on: “…”, content_type: "a"*1000}]. On PostgreSQL, update_all raises, the transaction aborts, and the API returns a 500 with no useful error; nothing is written.
Fix: Validate content_type length before update_all and return 422 if it exceeds the column limit. For example:
- limit = Attachment.columns_hash['content_type']&.limit
- if given[:content_type].present? && limit && given[:content_type].to_s.bytesize > limit
-   errors << extended_api_history_invalid(:content_type)
- end
Add this check in extended_api_history_attachment_errors, and only assign cols[:content_type] when valid.
Resolution: fixed in the next commit: filename, content_type and description longer than 255 characters (core's validation for filename and description, the string column on MySQL) are refused with 422 before anything is written; on PostgreSQL the columns have no limit, so there it was not a 500 but a value core would refuse. Test cases 'content type too long' and 'filename too long' fail without it.

Minor, app/controllers/extended_api_issue_histories_controller.rb:139
Problem: private_notes is only refused when it equals "true" or "1". The README states “any notes or private_notes” should be refused. For JSON clients, private_notes: true is covered, but other truthy representations (e.g., "on", "yes") pass the check and are silently ignored, contrary to the contract.
Concrete failure: A client sends {"journals":[{"user_id":1,"created_on":"…","private_notes":"on","details":[...]}]}. The request succeeds and stores a history journal, despite the presence of private_notes the docs say should trigger 422.
Fix: Refuse whenever the key is present (regardless of its value). Replace:
- errors << extended_api_history_invalid(:notes) if journal[:notes].present? || %w[true 1].include?(journal[:private_notes].to_s)
with:
- errors << extended_api_history_invalid(:notes) if journal.key?(:notes) && journal[:notes].present?
- errors << extended_api_history_invalid(:notes) if journal.key?(:private_notes)
Resolution: fixed in the next commit: private_notes is refused unless it is empty, false or 0 (so 'on', 'yes', true, 1 are refused); test case 'private notes on' fails without it.
