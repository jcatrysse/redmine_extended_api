Major, app/controllers/extended_api_issue_histories_controller.rb:120-134
On MySQL/MariaDB (no INSERT … RETURNING), journal IDs are derived by querying maximum(:id) on non-unique attributes (journalized_id, journalized_type, user_id, created_on) after each insert_all. Under concurrency or when multiple journals share the same timestamp/user/issue, this can pick the wrong row. That mis-associates JournalDetails and returns incorrect journal_ids in the API.
Scenario: Two concurrent imports write a journal on the same issue with identical created_on/user. The fallback path does Journal.insert_all([row]) for each row, then Journal.where(...).maximum(:id). It can return the other import’s id. Details for request A end up attached to request B’s journal; A’s response returns journal_ids that don’t belong to its payload.
Fix: In the MySQL path, make identification unique per row and then restore the final shape. For example:
- During insert, set a unique sentinel in notes (e.g., a SecureRandom.uuid).
- Read back the id via the sentinel: pick(:id) where notes == sentinel alongside the other keys.
- Immediately clear notes back to '' with update_columns.
Alternatively, use connection.insert (not insert_all) for single-row inserts and obtain last_insert_id from the adapter, ensuring no callbacks run, then proceed.
Resolution: fixed in the next commit: on MySQL/MariaDB the id is read with LAST_INSERT_ID() on the same connection right after each single-row insert, which concurrent requests do not share; other adapters without RETURNING (SQLite, development only) keep the read-back. Not run here: tests and production are PostgreSQL only (decision 2026-10-07), where the ids come from RETURNING.

Major, app/controllers/extended_api_issue_histories_controller.rb:158-188
Attaching uploads by token does not verify that the token belongs to an unattached upload (container_id/container_type nil). If a token remains on an already-attached attachment (or is reused), this endpoint will silently “move” that file to the target issue. This is contrary to the documented contract (“uploads from /extended_api/uploads.json”) and can lead to data loss on the original container.
Scenario: An admin accidentally supplies the token of an attachment already linked to Issue A; calling POST /extended_api/issues/B/history.json with that token will reassign the attachment to Issue B, removing it from Issue A.
Fix: In extended_api_history_attachment_errors, after finding the attachment by token, require it to be unattached:
- errors << invalid(:token) unless attachment && attachment.container_id.nil? && attachment.container_type.nil?
Also enforce the same check in attach_extended_api_history_files before update_columns and raise/render 422 if violated.
Resolution: not a defect, now proven by a test: core's Attachment.find_by_token returns nil for an attachment that has a container (attachment.rb `attachment.container.nil?`), so an attached file's token is refused with 422 'Token is invalid' before anything is written; test test_history_refuses_the_token_of_an_attached_file (second call on another issue: 422, file stays on issue 1).

Minor, app/controllers/extended_api_issue_histories_controller.rb:158-188
After successfully attaching the upload to the issue, the token is left unchanged. Core clears tokens once an upload is attached; keeping it allows indefinite reuse of the same token (even though this endpoint is admin-only) and breaks the usual “token is single-use” assumption.
Scenario: After a history import attaches an upload to an issue, the same token can be reused in later calls to move that same attachment again (compounded with the previous issue).
Fix: When updating the attachment, also null the token: include token: nil in cols passed to update_columns.
Resolution: not applicable: an attachment has no token column; the token is computed from id and digest (Attachment#token), core clears nothing either. Reuse after attaching is refused by find_by_token (see the previous finding and its test).
